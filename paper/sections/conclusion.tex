\section{Conclusion}

\subsection{Target Environments}

Our approach delivers maximum impact in constraint-based environments where inversions are cheap and commitments are expensive. \textbf{Arithmetized systems} (R1CS, Plonkish/SCS) benefit because Schwartz-Zippel evaluation is efficient and field inversions cost only 2C. \textbf{Recursive proof systems} benefit most directly: the 60\% commitment reduction compounds at each recursion level, since each commitment in the inner circuit becomes a constraint in the outer circuit. \textbf{ZKVMs} (RISC Zero, SP1, Jolt) benefit naturally as they express computation as constraint systems compatible with our polynomial framework. \textbf{Calldata-constrained blockchains} (Ethereum L2s, BitVM) also benefit, as fewer commitments means smaller proof transcripts.

\subsection{Implementation and Performance}

Table~\ref{tab:main_performance} presents benchmark results from our gnark implementation of the polynomial ring toolkit, measured on a Groth16 verification simulation on BN254. Our theoretical analysis (Section~\ref{sec:op:comp:our}) predicted 46\% constraint reduction and 75\% commitment reduction per zero-bit step. The end-to-end results confirm both directions of saving: \textbf{39\% SCS constraint reduction} (1,890,771~$\to$~1,158,194) and \textbf{60\% commitment reduction} (739,198~$\to$~295,946), with strong secondary improvements across compile-time memory ($\sim$42--43\%) and solver memory ($\sim$26\% SCS, $\sim$52\% R1CS).

\paragraph{Benchmark circuit.}
Both implementations were evaluated against the identical \texttt{Groth16Simulation} circuit\footnote{Circuit definition: \url{https://gist.github.com/shramee/6b02bea91e25634108338b9bce384e5e}}, which faithfully models the pairing checks performed during Groth16 proof verification:
\begin{itemize}
  \item \textbf{Step~1:} A 2-pair fixed-$\mathbb{G}_2$ pairing check $e(P_1,Q_1)\cdot e(P_2,Q_2)=1$, where both $\mathbb{G}_2$ points use precomputed line evaluations (\texttt{PairingCheck} with fixed $Q$).
  \item \textbf{Step~2:} A single in-circuit Miller loop $\mathrm{ML}(P_3,Q_3)$ combined with a Miller loop result $f$ computed \emph{outside} the circuit, followed by a final-exponentiation-equals-one assertion (\texttt{AssertMillerLoopAndFinalExpIsOne}).
\end{itemize}
This structure directly mirrors real Groth16 verification: the two fixed-$\mathbb{G}_2$ pairings correspond to the key-pair checks, while the combined inside/outside Miller loop models the proof-element pairing with a partially precomputed contribution.

The \textbf{gnark baseline} numbers were obtained by running \texttt{BenchmarkGroth16Simulation} against the upstream gnark \texttt{emulated} package (\texttt{github.com/consensys/gnark}). The \textbf{This Work} numbers were obtained from the same benchmark file compiled against our fork\footnote{Our implementation: \url{https://github.com/mistcash/tiny-gnark/tree/ppp}}, which replaces the per-multiplication deferred checks in the \texttt{emulated} package with the polynomial ring toolkit described in this paper. No changes to the circuit definition or test harness were required; only the underlying \texttt{emulated} arithmetic backend differs between the two runs.
The Garaga library~\cite{grg} provided an earlier proof of concept for this technique in Cairo/Starknet (2024) but lacked a systematic comparison against an industry baseline; this work provides that comparison against gnark, the standard framework for field emulation in arithmetized circuits.

\subsection{Final Remarks}

We have shown that choosing the right granularity for polynomial identity testing---entire Miller loop steps rather than individual multiplications---yields substantial and measurable improvements. The key technique, collapsing a composite multi-operand product into a single Euclidean division check with batched quotient accumulation, is simple to implement and broadly applicable to other multi-step cryptographic computations in arithmetized environments.

Our polynomial ring toolkit is implemented in gnark's \texttt{emulated} package and is available as a reusable, parameterised library for any emulated field and modulus polynomial. We hope this work encourages further exploration of polynomial batching granularity as a design axis for constraint-system implementations.
