\section{Conclusion}

We have shown that choosing the right granularity for polynomial identity
testing---entire Miller loop steps rather than individual field
multiplications---yields substantial and measurable improvements in
arithmetized pairing verification.
The key technique, collapsing a composite multi-operand product into a single
Euclidean division check with batched quotient accumulation, is simple to
implement and broadly applicable to other multi-step cryptographic computations
in arithmetized environments.

\subsection{Applications and Impact}

Our approach delivers maximum impact in resource-constrained execution environments where custom auxiliary data can be provided for cheaper verification. \textbf{Recursive proof systems} benefit the most, greatly reducing outer circuit complexity through fewer commitments and operations. \textbf{ZKVMs} (RISC Zero, SP1, Jolt) benefit naturally as they express computation as constraint systems compatible with our polynomial framework. \textbf{Calldata-constrained blockchains} (Ethereum L2s, BitVM) also benefit, as fewer commitments mean smaller proof transcripts and associated calldata costs.

This is already implemented in-production in Garaga~\cite{grg} for CairoVM and is currently the standard for all pairing based ZK proofs on Starknet. The polynomial ring toolkit (Section~\ref{sec:polyring}) in gnark, submitted as a part of this work, will directly impact the \texttt{evmprecompiles/ecpair} precompile via \texttt{AssertMillerLoopAndFinalExpIsOne}.

\subsection{Implementation and Performance}

\textbf{The Garaga implementation~\cite{grg}}
in Cairo/Starknet (2024) sufficiently reduced the commitment overhead and modulo operations (Table~\ref{tab:garaga_performance}) to fit Groth16
proof verification within Starknet's transaction limits for the first time.
However, Cairo~\cite{cairo} is a specialized environment with its own cost metrics,
making direct comparison with mainstream ZK frameworks difficult.
This work situates the same technique within gnark---the standard framework for
field emulation in arithmetized circuits---providing a systematic benchmark against
an industry baseline.

\begin{revblock}
In Table~\ref{tab:garaga_performance}, the \emph{Before} column is Garaga verifying each extension field multiplication individually via the polynomial identity testing of~\cite{FXFM23}; the \emph{After} column is Garaga using our consolidated relations. MULMOD/ADDMOD count modular field operations, COMMITS count Poseidon~\cite{poseidon} input commitments for Fiat-Shamir, and VM STEPS count CairoVM CPU cycles---together a low-level estimate of computational complexity inside the virtual machine.

\paragraph{Our polynomial ring toolkit} implementation in gnark is benchmarked in Table~\ref{tab:main_performance}, measured via a 3-pairing product check (see below) on BN254 and BLS12--381. We compare our results against a \textbf{gnark baseline} using the upstream \texttt{emulated} package~\cite{gnark}, which represents the state-of-the-art for emulated pairings and includes the optimizations of~\cite{PR1CS22} and~\cite{OPP24}.

The \textbf{This Work} numbers were obtained by compiling the exact same benchmark against our fork, replacing the baseline's extension field multiplications with our new toolkit. No changes were made to the circuit definition or test harness. Both implementations exploit the sparseness of the Miller line functions (Section~\ref{sec:ops:comp-analysis}).

\paragraph{Benchmark circuit.}
\label{sec:bench-circuit}
Both implementations are evaluated against the same gnark circuit: a 3-pairing multi-pairing check $\prod_{i=1}^{3} e(P_i, Q_i) = 1$ via \texttt{PairingCheck}. This corresponds to the pairing workload of a Groth16 verification, which reduces to a product-of-pairings check over three variable pairs once the constant $e(\alpha, \beta)$ term from the trusted setup is folded in. The same 3-pairing configuration is used in the CairoVM benchmarks of Table~\ref{tab:garaga_performance}, allowing a like-for-like comparison across environments.

Test circuit can be found at \texttt{sw\_bn254} package in \texttt{g16\_simulation\_test.go} file in our implementation repo - \url{https://anonymous.4open.science/r/tiny-gnark-DDCD/}.
\end{revblock}

\subsection{Further Work}

Several natural extensions of this work remain open. First, the framework
can be readily extended to additional curves \rev{beyond BN254 and BLS12--381, notably
\textbf{BW6--761} for recursive proof chain verification on Ethereum}.
A further direction is exploring the technique for native field pairings, such
as BLS12--377 inside BW6--761~\cite{PR1CS22}, where the
trade-off between batching savings and commitment costs warrants dedicated
analysis.

Finally, the underlying technique generalizes beyond pairings to any setting
involving repeated operations over the same polynomial rings. Another interesting
instance is lattice-based cryptography in ZK-SNARKs: schemes such as ML-KEM and
ML-DSA operate in cyclotomic rings over $\mathbb{Z}_q[x]/(x^n + 1)$.
Though the small moduli typical of lattice based schemes don't require active
reductions, the polynomial identity testing would help in two significant ways.
One, skip the need to do the in-circuit NTT transforms, and two, provide reduced
coefficients ready for efficient packing for public inputs.

Exploring the cost-benefits of this approach in lattice-based ZK-SNARKs is another
promising direction for future work.
\end{revblock}
